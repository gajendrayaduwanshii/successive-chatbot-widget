# Successive Content API Audit

Audit date: 5 August 2026 (Asia/Kolkata)

This document records which Successive WordPress APIs are reachable, which ones expose usable content, and how the chatbot should retrieve page and post data. Counts are live-site snapshots and will change as content is published or removed.

## Executive summary

- Both requested APIs return HTTP `200`: `/wp-json/wp/v2/pages` and `/wp-json/wp/v2/posts`.
- Pages: 171 published records, but only 49 have a non-empty REST body. Of these, 47 contain a short summary under 500 characters. Only Privacy Policy and Terms of Services contain substantial, near-complete REST content.
- Pages: 122 records have empty `content.rendered` and `excerpt.rendered`.
- Public page HTML provides substantial `<main>` content for 169/171 pages. Page HTML hydration is therefore required.
- Posts: 731 published records and 730 have non-empty REST body and excerpt content.
- One post has no REST body: `ui-vs-ux-e2-80-8a-the-yin-yang-of-product-design`.
- The users API is intentionally not used by the chatbot.

## What “working” and “complete” mean

| Classification          | Meaning                                                                        |
| ----------------------- | ------------------------------------------------------------------------------ |
| Endpoint working        | Endpoint returns HTTP `200` and valid JSON.                                    |
| Record available        | Title, slug, link, ID and metadata are returned.                               |
| REST content available  | `content.rendered` contains readable text.                                     |
| REST content complete   | REST content is close to the substantial content visible publicly.             |
| HTML hydration required | REST metadata works, but rendered `<main>` must be fetched for the page story. |

An endpoint can be working while its content fields are empty. This is the main issue with Successive service pages and custom post types.

## Pagination and search behavior

WordPress limits `per_page` to 100:

```text
?per_page=100&page=1   valid
?per_page=101          HTTP 400
```

Read these headers and fetch all pages:

```text
X-WP-Total
X-WP-TotalPages
```

Useful examples:

```text
# Exact page lookup
GET /wp-json/wp/v2/pages?slug=custom-web-app-development

# Page metadata search
GET /wp-json/wp/v2/pages?search=custom%20web%20app%20development&per_page=20

# Post search
GET /wp-json/wp/v2/posts?search=artificial%20intelligence&per_page=20

# Embedded author/featured-media metadata
GET /wp-json/wp/v2/posts?per_page=100&page=1&_embed=1
```

Slug lookup is more reliable than full-sentence WordPress search. A sentence copied from a service page may not return that page because its REST body is empty. The chatbot should resolve the canonical slug, fetch its REST record, then hydrate its public `link`.

## Recommended chatbot retrieval flow

1. Fetch configured collections with `per_page=100` and follow `X-WP-TotalPages`.
2. Use post REST bodies directly, except empty records.
3. For pages, retain REST metadata and hydrate the public `link` when content is empty or too short.
4. Extract readable public content from `<main>`.
5. Index title, slug, headings and paragraph-preserving chunks.
6. Prefer an exact canonical slug over generic search for known service topics.
7. Keep service queries on service pages; do not substitute unrelated blogs when a relevant page exists.
8. Use posts for blog/resource intent and `case_study` for explicit case-study intent.
9. Return only sources that contributed to the answer.
10. Return a grounded fallback if neither REST nor HTML supplies reliable content.

## Intentionally excluded API

The users endpoint responds, but it must not be used:

```text
https://successive.tech/wp-json/wp/v2/users
```

It is unnecessary for content answers and was explicitly excluded from scope.

## Known limitations

- Counts and content can change after the audit date.
- HTTP `200` does not guarantee useful body content.
- Page-builder/template content is often absent from REST.
- Public HTML structure may change; `<main>` extraction must fail safely.
- REST search cannot search page text omitted from REST.
- REST `search` is broad keyword matching, not semantic retrieval.
- `scan` has no conventional `<main>` section.
- ACF is not publicly populated in audited responses.
